## What the synthesis got right

**The silent failure epidemic is the most important finding in the document.** The synthesis correctly identifies this as the median behavior of deployed systems, not an edge case. What makes it useful is the specificity: TencentDB advancing the cursor unconditionally on extraction failure, mem0's JSON truncation dropping facts silently, SimpleMem's Tantivy index frozen at first batch. These are documented, reproducible, production behaviors. Any architecture that doesn't treat "extraction failure leaves no trace" as a first-class design constraint will reproduce all of them.

**The "static lore outperforms dynamic memory" finding is real and important.** Three independent platforms document this independently — Replika, RisuAI, SillyTavern — and the synthesis is right to call it an empirical field observation rather than a fundamental law. The correct implication is a build order: get the static layer correct and reliable before investing in dynamic recall. Most teams skip directly to the interesting retrieval problem and then wonder why users are pasting context manually at session start.

**The observation that the field wasn't built for companions is structurally correct**, and the list of small personal projects that came closest (mnemosyne, soul-of-waifu, paramecium, memory-constellations) is accurate. These four products contain design decisions that appear nowhere in any funded product. The synthesis is right to elevate them.

## What the synthesis missed or underweighted

**Speaker misattribution is a systemic problem, not an isolated honcho bug.** The synthesis buries it inside the honcho entry. But look at how many systems extract from conversation without distinguishing speaker: mem0's extraction prompt is only partially separated (separate prompts for user vs. assistant memory, but the cross-scope entity linking still merges them), honcho's deriver actively misattributes AI speech to the human user, hermes-agent stored routing metadata as user-authored content. This is a structurally widespread failure. A companion that builds its model of the user partly from what it said itself will drift toward a self-confirming mirror, not a model of a real person. The synthesis should have flagged speaker attribution as a first-tier requirement alongside subject contracts.

**The "never admit no information found" scaffold instruction deserved its own named failure mode.** The synthesis mentions it under companion-specific gaps but doesn't elevate it to the prominence it deserves. This isn't a retrieval failure — it's an explicit design choice that manufactures confabulation. mem0's reader scaffold literally instructs the model not to admit a gap. This is a companion-destroying default. A companion that confidently fabricates details about a user's life, based on a failure to retrieve, and cannot be distinguished from a companion recalling accurately, will be discovered eventually. When it is, the relationship is over. This failure mode is worse than forgetting.

**The model/service update as memory reset is a major unaddressed pattern.** This appears in characterai (auto-memory stopped picking up details after a recent update), replika (post-2.0 rollout caused partial memory loss and personality drift), nomi (post-update degradation breaking memory and personality coherence), kindroid (LLM model updates cause loss of established character memory), and supermemory (upgrade-induced memory unsearchability reported across multiple versions). The synthesis doesn't synthesize this. It's not a storage problem — it's a deployment-level problem where the memory store is valid but the model behavior shifts, effectively resetting the relationship. No product in the field has an architecture that survives model updates with continuity intact. This is a serious blind spot for anyone shipping a companion.

**The CharacterAI emotional context recall finding is the most important observation in the entire document and the synthesis underweights it.** The synthesis quotes it: "current memory does not surface the right fact at the right emotional moment." It then moves on. This should have been the organizing principle for the entire synthesis. It reframes the problem from "did the right passage come back" to "does the system have a speak/silent policy that reflects what matters emotionally, not just what is semantically similar." No product has solved this. ombre-brain comes closest with its SurfacePolicyVM, but even that doesn't measure whether the policy actually improves relationship quality. The synthesis names it, then doesn't draw the right conclusion: the benchmark that matters doesn't exist yet, and building it is more important than optimizing LoCoMo scores.

**The cost dimension is absent.** claude-mem hit 64% of the user's primary model spend on memory processing. kiwi-mem estimates $0.22/day for active use with local embeddings. SimpleMem's intent-aware retrieval planning adds multiple LLM calls per turn. For a companion that runs continuously over months, these numbers determine what's commercially viable. The synthesis doesn't mention cost at all.

## What the synthesis overweighted

**taosmd is elevated as the reference architecture, but too many of its named features are broken to justify that position.** The synthesis credits taosmd for intellectual honesty — documented benchmark corrections, published hallucination rates — and that honesty is genuinely valuable. But the same documentation that makes it trustworthy also reveals: temporal boosting silently broken (writes to wrong field), KG edge directionality broken (incoming and outgoing branches are identical dead code), contradiction detection only on hardcoded predicates, LLM reranker exists but is never called in the retrieve() orchestrator, staleness axis not meaningfully evaluated. The claims gate and zero-loss archive are real and worth stealing. The five-layer architecture is a useful reference. But describing it as the foundation to combine with paramecium and mnemosyne treats an architectural diagram as production-ready infrastructure. The synthesis would be sharper if it said: steal the zero-loss archive and claims gate, treat the rest as specification rather than implementation.

**The benchmark numbers section is too long for how little it matters.** The synthesis correctly concludes that the numbers are nearly incomparable, then spends significant space comparing them anyway. LoCoMo and LongMemEval measure retrieval accuracy on documented conversations. They don't measure behavioral continuity, emotional appropriateness of recall, or relationship coherence over time. The CharacterAI finding explains why: users aren't complaining about retrieval accuracy. They're complaining that the companion behaves as if the past didn't happen. A companion that scores 94.7% on LoCoMo can still feel amnesiac if its speak/silent policy is wrong. The synthesis should have used the benchmark section to argue that the right benchmark doesn't exist yet and sketch what it would look like — not to compare incomparable vendor numbers.

**The list of "what a companion memory system needs" treats aspirational and foundational requirements as equally necessary for v1.** Emotional state tracking with decay tied to emotional processing, relational quality tracking, circumplex affect models — these are the right long-term targets. But presenting them as co-equal requirements with zero-loss archive and subject-attributed facts sets the wrong build order. A companion with a reliable, hallucination-checked, speaker-attributed fact store that admits uncertainty is far ahead of anything in the field, even without affect modeling. The synthesis doesn't distinguish between "required to be better than the field" and "required to be the best possible companion."

## Top 5 design decisions worth stealing

**1. Quote-verification guard (paramecium)**
Before any extracted memory enters the store, the system checks that the verbatim source quote exists in the source batch. If the quote can't be found, the memory is dropped. This directly targets the extraction hallucination problem: taosmd documents 18.8% of LLM-extracted facts as partially or unsupported; paramecium's prior pipeline produced 36% paraphrase rather than verbatim content. The guard eliminates the class of fabricated memories that have realistic texture and can't be detected after the fact. It adds one string-search per extracted fact at write time. No other product implements this.

**2. MEMORY.md / USER.md split (soul-of-waifu, structural parallel in hermes-agent)**
Character psychology (beliefs, emotional state, internal tensions, self-model) and user-facing facts (name, preferences, relationship history, shared milestones, promises) are stored as separate schemas with different write paths and different authorities. The character owns the first store; the user's behavior populates the second. This distinction is foundational — a companion that conflates "what I believe about myself" with "what I know about you" will produce incoherent behavior as both evolve. No funded product makes this split structural.

**3. Zero-loss append-only archive as rebuild target (taosmd)**
Every ingested message goes to an append-only archive unconditionally before anything else. All other layers — the curated fact store, the vector index, the knowledge graph — are derived from the archive and rebuildable if they're wrong. When a bug corrupts the derived layer, you reindex from the archive instead of losing data. When you improve your extraction pipeline, you can reprocess history. This is the right source-of-truth architecture. It also means the product is honest about what it actually has: a verifiable raw record, not just a model's interpretation of the past.

**4. Reads-never-reinforce; explicit promote-only strengthening (vestige, paramecium, ombre-brain)**
Retrieving a memory does not increase its retrieval score. Only an explicit positive outcome signal strengthens a memory. Three products independently converge on this. The failure mode it prevents: a highly-retrieved fact becomes confidently wrong when the user's circumstances change (mem0 acknowledges this as a known trade-off under their ADD-only architecture). If retrieval reinforces, the companion is most confident about the facts it has surfaced most often — which may be exactly the ones that are now stale. Self-reinforcing retrieval makes highly-retrieved memories confidently wrong at the worst possible moment.

**5. Echo lane retrieval (paramecium)**
At retrieval time, two separate query vectors are issued: one from the user's message, one from the companion's previous reply. The second lane surfaces memories relevant to what was just said by the companion, not only to what was just asked by the user. This matters because companions frequently use phrasing, metaphors, and callbacks to their own prior statements. A memory that isn't semantically similar to the user's message may be highly relevant to the thread of what the companion was discussing. This is a two-vector retrieval at negligible incremental cost with documented value for companion-style conversations.

## Top 5 failure modes to build against

**1. Silent cursor advancement on LLM extraction failure (TencentDB, memu)**
The extraction pipeline calls the LLM, receives an error (429, timeout, truncated response, credential failure), and then marks the source batch as processed anyway. Those conversations are dropped from the curated layer forever with no log entry distinguishing "processed, nothing noteworthy" from "failed, never processed." TencentDB documents this three times in their own issue tracker. memu documents cursor advancing before commit. The fix is simple — mark batches as failed, not complete, on extraction error — but most products don't do it. A companion that silently stops learning after a transient API error, with no visible signal, is the baseline failure mode.

**2. AI-generated speech attributed to the user (honcho, hermes-agent)**
The extraction pipeline lacks explicit speaker attribution rules. honcho's deriver misattributes AI agent speech to the human user. hermes-agent stored routing metadata as user-authored content. mem0 has partial separation but entity linking still merges across scopes. The resulting model of the user is a blend of what the user said and what the companion said, with no way to distinguish the two post-hoc. A companion that builds its model of you partly from its own prior outputs will drift toward a self-confirming mirror. The fix requires explicit speaker tagging at ingestion, enforced in the extraction prompt.

**3. "Never admit no information found" fabrication instruction (mem0, replika pattern)**
Some systems include a scaffold instruction telling the model to produce a response even when retrieval returns nothing relevant, rather than admitting the gap. mem0's reader scaffold explicitly instructs the model not to acknowledge retrieval failure. This is an active design choice to manufacture confabulation. For a companion, the failure mode is worse than missing a fact: the companion confidently describes an event the user never shared, and the user cannot distinguish this from genuine recall. Discovery destroys trust in everything the companion has said. The correct design is the mnemosyne approach: abstain rather than fabricate when the corpus doesn't contain a relevant memory.

**4. False memory injection from distillation (aelios)**
aelios documents the clearest case in the field: the dream distillation pipeline fabricated a specific event (user complained about something after work) that existed in none of the 233 source messages for that day. The companion repeated it as fact. The user caught it only by manually checking every raw message. The fabricated memory had realistic texture — neither agent nor user could self-verify. This isn't an extraction hallucination on a vague semantic boundary; it's a specific event with specific details that never happened. Any distillation or summarization pipeline that produces condensed narrative summaries from message batches carries this risk. The quote-verification guard (paramecium) is the right mitigation; the zero-loss archive is the right recovery path.

**5. Self-reinforcing retrieval making stale facts confidently wrong (mem0, kindroid embedding lock, vestige)**
When a user's circumstances change — new job, ended relationship, moved city — the old fact doesn't just sit in the store with declining relevance. Under most architectures it's been retrieved many times and has high retrieval weight. It continues to surface at high confidence. mem0 acknowledges this as a known trade-off. kindroid added a "Deprioritize" user-facing knob specifically to address embedding lock. vestige's entire reads-never-reinforce architecture was designed to prevent it. The failure mode is a companion that confidently describes your life as it was eighteen months ago, not because it forgot to update, but because it remembers too reliably.

## What to build first

Build the write path, not the retrieval path. Specifically: an ingestion pipeline that produces a zero-loss append-only archive plus a curated fact store where every extracted claim includes a verbatim source quote, a speaker attribution (user vs. companion), and a subject label. Run the quote-verification guard at write time — any extracted claim whose verbatim quote can't be found in the source batch is dropped before persistence. Then write a behavioral continuity test script: a scripted relationship history of 20–30 turns that establishes facts about the user (name, job change, ended relationship, made a specific promise), followed by 10 follow-up prompts in emotionally-charged contexts where a human judge scores whether the companion referenced the past appropriately, fabricated anything, or behaved as if the conversation never happened. Run that test against CharacterAI, Replika, and your system with the same history. That comparison is the number to bet the company on — it directly measures the CharacterAI failure mode that the field hasn't solved, it's reproducible by anyone with access to those products, and it tells you whether the write path is working before you build retrieval optimization on top of it.

## The sharpest open question

Can LLM extraction at write time ever reach companion-grade trustworthiness, or does the write path need a fundamentally different architecture? The audit accumulates converging evidence against extraction pipelines: taosmd measures 18.8% partially or unsupported facts across 526 claims; paramecium's prior pipeline produced 36% paraphrase before building the quote-verification guard; aelios documents a fabricated event with realistic texture that neither the agent nor user could self-verify; honcho misattributes AI speech to the human user by default. The mitigations (quote verification, speaker attribution, claims gate) improve precision but each addresses one failure mode at a time. The deeper question is whether a pipeline that uses an LLM to decide what to remember about a real person — someone who will notice when the memory is wrong — can be made reliable enough that users trust it the way they trust a human who remembers them. The alternatives documented in the audit are: human-in-the-loop review gates (aelios, byterover), model-self-authored memories via structured tags (omemo builtin mode, paramecium's `<mem>` tag path), and append-only with manual curation (kimi-core's adversarial stance against AI self-management). None of these scale cleanly to continuous passive use. The audit shows every product has chosen a write architecture and shipped it; no product has measured whether users trust the output enough to rely on it emotionally. That measurement is what's missing, and it has to come before the architecture is locked in.
